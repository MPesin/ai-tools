# Orchestrate

The same flow as `/dev-flow:dev-plan` or `/dev-debug:dev-debug` followed by `/dev-flow:dev-implement`, with the same agents, files, commits and hooks, run end to end in one turn. What changes is who answers at the gates, the man-in-the-middle steps where those skills stop for the user: here `dev-flow:dev-orchestrator`, a clean-context agent that reads the code as it is and the change under way, compares the artifact of each gate with the specs and the acceptance criteria, decides by rule, per item or by score as `gates.md` says, rules in the user's place when one way is clearly best, and asks the user when it is not sure or when the specs do not settle the choice. The gates, the rulings open at each, the checks, the scoring, the budget and the files are defined in `${CLAUDE_PLUGIN_ROOT}/skills/orchestrate/gates.md`; read it first, with `${CLAUDE_PLUGIN_ROOT}/skills/dev-implement/plan-format.md`.

## Hard rules

- Everything in the `dev-plan`, `dev-debug` and `dev-implement` skills holds. This skill changes one thing: at the gates `gates.md` lists, the orchestrator's ruling stands in for the user's reply. Every other point where those skills stop for the user, and every ruling of `ask`, goes through **Escalation** below: the run stops exactly where the skill would wait for the user, and the user is told.
- Never push or open a PR unless the user asked for it at kickoff (recorded in `specs/decisions.md`); then the main session does both once, at the end of the run after gate I5 accepts, before the final report, so the PR carries the final code. Not after each commit, not at the human-review gate. Never merge, comment, publish or update a work item; never revert or discard a change; never edit a spec; never drop or weaken an acceptance criterion.
- A prompt to the orchestrator carries the task folder, the project root, the gate id, the question with the rulings open to it, and the paths to read (at I1 also the agent's report, verbatim, as data). Never your own conclusion, summary or recommendation. The orchestrator writes `orchestration.md` and `conformance.md` only; you act on its ruling, in the stage's own skill.
- Keep `orchestrate: on` in `plan.md` frontmatter: set it after every return of the planner or the debugger (they rewrite the file), before every orchestrator call, and whenever you set `status`. The other skills' stand-in clause, the hooks and `/dev-flow:load-flow` read it.
- Do not end the turn in the middle of the run. A turn ends only through Escalation or at the final report. Progress goes in short lines between tool calls.
- Budget per `gates.md`; a spent budget asks.

## Kickoff

1. The input is a task description, a bug (a report, a stack trace, a failing test, a bug work item), a work item reference, or a task folder or plan path (**Resuming**, below).
2. Checks, while the user is present; a failed check is a plain message with the choices, not an escalation, since no task folder exists yet: HEAD is on a branch (a detached HEAD is the user's to fix); no `planning` pointer exists and no `current` pointer names another task (if one does, say whose it is and what the flow skill's Start offers: finish or abandon it, or run this task in a worktree); for a bug, the `dev-debug` plugin is installed. Choose the flow: a bug whose cause is not confirmed goes through `dev-debug` (a bug whose cause the user has confirmed is planned like a feature); everything else through `dev-plan`. The user can name the flow ("orchestrate plan ...", "orchestrate debug ...").
3. Specs. The orchestrator judges against them, so the run needs them. If the user gave none, ask once, in the kickoff message: "Paste the PRD/HLD sections or the acceptance criteria, or give a work item reference; every decision of the run is checked against them. Or say `from the description` to derive acceptance criteria from the task text alone." That is the only question this skill asks before the flow starts.
4. Run the flow skill's Start step 1 (`dev-plan` or `dev-debug`): it creates the task folder and writes the `planning` pointer (`dev-debug` also writes the `plan.md` stub). Then save the specs per that skill's intake (`plan-format.md` Specs intake for a plan, `diagnosis-format.md` for a bug report); with `from the description`, save the task text as `specs/task.md` with the header line (the planner derives the criteria, and `conformance.md` says the baseline is the task text). Record the run parameters verbatim in `specs/decisions.md` under `## Kickoff <date>` (format in `gates.md`): whether to push and open the PR at the end (default: no), budget changes, constraints ("do not touch X"), anything else the user said about how to run. Skip the flow skill's own specs question (step 2 of `dev-plan`, step 2 of `dev-debug`): the intake is done. Once `plan.md` exists, list `specs/decisions.md` in `specs:` and set `orchestrate: on`.

## The plan flow

Run `dev-plan` in full, in draft mode (interactive planning needs a person), with these substitutions:

- After every planner return: set `orchestrate: on` again. Open questions that are not None: gate **P1**. Pass the answers to the same planner via SendMessage, each with its citation, as decisions; it updates `plan.md`. Asked questions stop the run (**Escalation**).
- The critic always runs (with specs saved, the lite criteria never hold). After it: gate **P2**. `revise`: the planner applies the accepted items (SendMessage, or a fresh planner pointed at `plan.md` and `plan-critique.md` with the accepted IDs; one planner revision), then a fresh critic writes `plan-critique.md` again; at most two critic rounds. `proceed`: on to approval.
- Approval: gate **P3**. `approve`: run **On explicit approval** of `dev-plan` in full (`status: approved`, `mode`, `orchestrate: on`, delete the `planning` pointer), then **The implement flow** below in the same turn, as `dev-plan` handles "fix the critique and start implementing". `revise`: back to the planner (one planner revision), P2 again if the critic's items changed, then P3. `ask`: `status: draft`, the pointer stays, **Escalation**.
- "Already done on the branch": gate **P3** on the close-out. `approve`: `dev-plan`'s close-out (`status: done`, delete the pointer), then a standalone QA note (the `dev-qa-impact` skill's steps), gate **I5** on it (a row to fix is asked, since nothing implements), and the final report. `revise`: plan the rest.

## The debug flow

Run `dev-debug` in full with these substitutions:

- Intake takes the bug report from the kickoff; its one question is not asked again. Set `orchestrate: on` after every debugger return and after the fix plan is written.
- After the debugger: `violations.md` gained lines, or it reports it could not proceed: gate **I1** (`continue` re-runs the debugger pointed at its `diagnosis.md` with the facts; there is no re-plan at `diagnosing`). Then the diagnosis gate: gate **D1**. `second opinion`: a fresh debugger writes `diagnosis-2.md`, then D1 again on both. `fix` or `fix, and ...`: `dev-debug`'s steps 4 and 5, with gate **P3** on the fix plan before `status: approved` (the critic when `dev-debug`'s own rule calls for it, with gate P2 on its output); a P3 `revise` is applied by you, as `dev-debug` step 4 writes the plan, and counts as a planner revision; then **The implement flow** in the same turn. `already fixed`: `dev-debug`'s `already fixed` exit, then a standalone QA note, gate **I5** on it, and the final report. `ask`: `status: diagnosing`, the pointer stays, **Escalation**.

## The implement flow

Run `dev-implement` in full, Intake included, with these substitutions:

- Intake, by rule: on the default branch, create a branch (`git switch -c <name>`; the project's branch convention from its guidance and `git branch -r`, otherwise the task folder's name without the date). The user's own uncommitted work is left out of the flow's commits (listed under `## Context` as `dev-implement` says); never commit it, never set `commits: off`. `commits: on`. A `current` pointer that turns out to name another task, or a detached HEAD, stops through **Escalation** (the kickoff checks make this rare).
- After every agent returns, before committing: `violations.md` gained lines, or the agent reports a blocked step, a file it does not own, an impossible plan, three failed builds on one error, or a regression test that passed before the fix: gate **I1**. `continue`: commit as `dev-implement` says and go on. `replan`: `dev-planner` in harden mode on `plan.md` with what the ruling names, the critic when the change touches a contract (gate P2 on it), then the stage again. `ask`: **Escalation**; nothing from that agent is committed until the user rules.
- The review loop, as written. When `needs-decision.md` gains a disputed finding: gate **I2** before the next fix round; upheld findings join the fix list, dismissed ones are left out, and you remove the ruled lines from `needs-decision.md` (the ruling stays in `orchestration.md`). At `status: blocked`: gate **I3**. `continue`: `status: reviewing`, count the granted rounds; `ask`: stop at `blocked` through **Escalation**.
- Human review: set `status: human-review` as stage 4 says, then gate **I4** instead of waiting. `done`: stage 6. `fix`: stage 5 with the orchestrator's findings pasted verbatim into the triager's prompt as the comments (the triager knows pasted comments and PR references, not `orchestration.md`), the fixer, the commit, then gate I4 again (the send-back budget). Checklist additions the triager proposes are not appended during an orchestrated run; they go in the final report for the user to confirm.
- QA impact: stage 6, then gate **I5** on `qa-impact.md`. `accept`: push and open the PR now if `specs/decisions.md` records that the user asked for them at kickoff (stage 4's push and PR, from the main session), then the final report. `fix`: stage 5 on the rows, stage 6 again, then I5 again (the same send-back budget).
- A stop `dev-implement` itself prescribes (a commit that fails, a push rejected after the pull, anything it says to show the user and stop) goes through **Escalation** too, with the question written by you in the shape of `gates.md`.

## Escalation

Every stop of the run goes through these steps, whether it comes from a ruling of `ask`, a spent budget, a stop the underlying skill prescribes, or a check this skill makes:

1. Append one line to `needs-decision.md` in the task folder, in the format `gates.md` gives: `- <date> <gate id>: <the question>; orchestrator recommends: <option>; see orchestration.md` (for a stop without a ruling, the gate id is the stage, for example `I1` for an agent's stop, and "orchestrator recommends" is your reading). The Stop hook notifies the user on it.
2. Leave `status` where the underlying skill waits at that gate (`draft`, `diagnosing`, `implementing` or `reviewing` with the item, `blocked`, `human-review`, `qa-impact`); the pointer stays; nothing the question concerns is committed.
3. Show the user the orchestrator's `Question for the user` block as it wrote it (the question, each option with its score and why, what would settle it, the recommendation), the code context in two lines, the replies that settle it, and that `/dev-flow:orchestrate <task folder>` resumes the run once they have answered (the stage's own skill continues it by hand instead). For a stop without a ruling, write the question in the same shape yourself.
4. End the turn.

## Resuming

`/dev-flow:orchestrate <task folder or plan path>` (also how `/dev-flow:load-flow` hands over a plan with `orchestrate: on`): read `plan.md`, the last entry of `orchestration.md`, `needs-decision.md` and `specs/decisions.md`.

1. First, in every case, run the underlying skill's resume step for the plan's `status`, so this session holds the flow: `dev-plan` at `draft` and `dev-debug` at `diagnosing` write the `planning` pointer again; `dev-implement` Intake from `approved` on writes `current` again (its Intake runs in full, under this skill's substitutions). In a new session the hooks refuse every stage agent until that pointer is this session's.
2. Then look at `needs-decision.md`. Its escalation lines start with `- <date> <gate id>:`; any other line is a disputed finding for gate I2. An escalation with the user's answer (in the call, or in the conversation since): save the answer verbatim under `## Decision <date> (<gate id>)` in `specs/decisions.md`, remove the line (delete the file when nothing is left), and continue from that gate with the answer as the ruling; it binds the orchestrator from then on. An escalation without an answer: show it and stop (the turn ends; nothing new is appended). No escalation: continue from `status` and `review_round`, under this skill's substitutions.

## Final report

`dev-implement`'s final report (`status: done`, `orchestrate: on`, the pointer renamed to `finished`; a close-out has no `current` pointer, so say that the run ended at the close-out and no "done" notification follows), plus: the rulings per gate from `orchestration.md`, one line each with the winning option's total, its margin and the confidence, or the trigger that fired, or the per-item counts (so every choice of the run can be traced to its scores); `conformance.md`'s status column (every row Met, Not covered by provided specs, or Decided by the user, or the run would not have reached here); the escalations the user settled; the checklist additions proposed for the user to confirm; and whether the branch was pushed and the PR opened (when asked at kickoff), or both wait for the user.
