# Init Mode — thin CLAUDE.md of always-loaded rules

CLAUDE.md is force-loaded into every prompt; the repo-guide skill loads on
demand. Init writes ONLY what must be always-loaded and is NOT in repo-guide:
behavioral rules, workflow conventions, hard constraints, environment quirks.
Repo facts (purpose, stack, architecture, modules, symbols, commands, code
conventions, gotchas) live in repo-guide and are excluded here — coverage is
checked against the actual generated files, never assumed.

No repo-guide pointer in the output: project skills are auto-discovered and
the repo-guide description already fires on any task in the repo. A pointer
would be duplication.

## Procedure

1. **Prereq.** Read `.claude/skills/repo-guide/SKILL.md` and every file in its
   `references/` — this is the exclusion baseline. The prereq test: the skill
   dir exists AND is committed AND is not stale by the same threshold the hook
   uses — ≥20 commits on top of the last commit touching the dir:
   `git rev-list --count $(git log -1 --format=%H -- .claude/skills/repo-guide)..HEAD`
   (see freshness.md). Missing, never-committed, or stale → offer to run the
   full mapping pipeline first (SKILL.md Process steps 3-8), then return here;
   user declines or run is non-interactive → abort (init without a current
   repo-guide would pull repo facts into CLAUDE.md, which is exactly what this
   plugin exists to avoid). A guide under the threshold counts as current even
   if recent commits outdate details — init filters against it as-is and does
   not audit it.
2. **Harvest.** Scan the rule sources: `.cursor/rules/`, `.cursorrules`,
   `.github/copilot-instructions.md`, `CONTRIBUTING.md` (root or `.github/`),
   existing `CLAUDE.md` / `CLAUDE.local.md` (root and nested), `AGENTS.md`,
   `GEMINI.md` — plus any other agent-rule file noticed along the way; the
   list is a floor, not a ceiling. An agent-rule file is prose whose purpose
   is to instruct agents on behavior in this repo — session state, memory
   files, and permission/config JSON are not sources, and neither is the
   codebase itself. Extract candidate rules; drop every claim the repo-guide
   already covers. Do not invent rules — every candidate is traceable to a
   rule-source file or to the interview below.
3. **Interview.** One AskUserQuestion round (multiSelect where it fits):
   branch/commit/PR conventions; hard constraints ("never touch X", "never run
   Y"); environment quirks; anything else the user wants every agent to know
   before its first tool call. Frame every question to ask for what the
   repo-guide does NOT already record — do not solicit build commands, setup
   steps, or gotchas it covers; interview answers still pass the step-4
   filter like any other candidate. Skip the interview in non-interactive
   runs — harvest-only is valid.
4. **Filter.** For each candidate line ask: (a) would an agent need this
   BEFORE its first tool call? (b) is it absent from repo-guide? Both must be
   yes, or the line is dropped (and, if it is a repo fact worth keeping,
   noted as a suggestion for the next `/repo-map refresh` instead).
5. **Draft.** Zero surviving candidates → write NO file: give the step-7
   report with "nothing to write" as its outcome (step-4 drops and refresh
   suggestions still included) and stop — an empty always-loaded file is pure
   noise. If a CLAUDE.md already exists in that case, offer its
   migration/shrink instead (interactive runs only; otherwise note it in the
   report). Otherwise assemble the thin CLAUDE.md:
   - first line `<!-- generated by repo-mapper on <YYYY-MM-DD> -->` (this file
     never counts toward repo-guide freshness — its own history is just git)
   - imperative bullets under at most 3 headings; target ≤30 lines total
   - no repo facts, no repo-guide pointer, no duplication of any source
     that remains in the repo
6. **Approve.** Never write silently. Existing CLAUDE.md: show a
   current → proposed table and wait for approval (this subsumes the fat-
   CLAUDE.md migration offer — harvest IS the migration). No existing file:
   show the full draft and wait for approval.
7. **Report.** File written, line count, sources harvested and what each
   contributed; step-4 refresh suggestions go here as report text only (never
   into a file). Offer to commit. If a harvested source is now fully redundant
   (e.g. `.cursorrules` duplicated verbatim), offer its cleanup — never
   auto-delete, and skip the offer in non-interactive runs.

## Non-negotiables

- Never overwrite user content without the step-6 approval gate.
- Repo facts are excluded CATEGORICALLY — a fact the repo-guide misses is a
  refresh suggestion in the report, never a CLAUDE.md line. "Traceable to a
  source" means a rule-source file; citing code (a build script, a config)
  does not qualify.
- Exclusion decisions cite the covering repo-guide file when a candidate is
  dropped as "already covered", so the user can audit the filter.
